## Problem Statement

Plan 2 copies the C game into Lua, function by function, so that plan 3 can put any Lua function next to its C original when a replay diverges. Every value that is a `p8_fixed_t` in C is a PICO-8 16.16 fixed-point number, and the random generator is the C one (an LCG with a fixed default seed). Lua numbers are doubles: a Lua port that computes with them diverges from the C at the first overflow, truncation, division by zero or random draw, and every later replay frame diverges with it. Nothing under `game/` yet gives the Lua game the C numbers, so no step of Phase 2 or 3 can start.

Separately, the timing protocol every `make test` check is gated by (`docs/love-port/design.md` § "`make test` and the fake's checks", rule 4) names a plan-wide reference commit, `2e7215c`, that does not exist in this repository: the gate cannot be run as written.

## Solution

A Lua module, `game/p8/fixed.lua`, is the faithful copy of `src/p8/fixed.h` and `src/p8/fixed.c`: every constant, function-like macro, inline function, exported function and file-local function, in the C order, with the C names, computing the same 32-bit results bit for bit with LuaJIT's `bit` library. Its sine table is the faithful copy of `src/p8/quarter_wave.h`, `game/p8/quarter_wave.lua`, generated by the same generator as the C header.

Proof of equality: a small C binary links the C library and emits, for generated inputs, each input and the C result; a LuaJIT test in `tests/lua/` feeds the same inputs to the Lua module and fails on the first differences, naming function, inputs, expected and actual values. `make test` runs it as its own parallel target, inside the timing rules; if the full sweep of millions of values does not fit the budget, the edge values and a budget-sized sample stay in `make test` and the full sweep moves to its own target outside `make test-all`.

Before any check is added, the step names a replacement reference commit present in this repository, in the design file and in the step note, so the timing gate of this step (and of every later one) can actually run.

## Implementation Decisions

### Reference commit (first, before any check)

- The replacement for `2e7215c` is `8dff812`, the merge of pull request #1 that put the cleaned fork, the fake LÖVE and its checks on the main branch: the last commit before plan 2's own work, with the `make test` every plan 2 step starts from. (`0a04920` lacks the fake checks; `5a3eb2b` and `b9bb7c9` change docs only.)
- `docs/love-port/design.md` rule 4 names `8dff812` in place of `2e7215c`; the old figures (4 cores, 7.70 s over 15 runs) are replaced by this step's measurement of `8dff812` on the container, with core count.
- A step note `### Step 1.2` is added under `## 6. Step notes` of `docs/love-port/plan-2.md`; it names the reference commit and why, and later holds the measurements and the out-parameter convention.

### The Lua module

- One module per C pair: `src/p8/fixed.h` and `src/p8/fixed.c` become one Lua file in `game/p8/`, required as `p8.fixed` (the game directory is the Lua root, as under LÖVE). Order: the header's constants, macros and inline functions in header order, then the `.c` functions in `.c` order, the file-local helpers where the `.c` defines them. The module returns one table whose fields carry the exact C names, each function defined as a field at line start so the checklist sees it (see Checklist coverage).
- Constants: `P8_FIXED_SHIFT`, `P8_FIXED_DIV0_POS`, `P8_FIXED_DIV0_NEG` are fields with the C values. The private LCG constants and default seed are module locals with the C names.
- Function-like macros: `P8_FIXED_INT(i)` is a function equal to `p8_fixed_from_int`; `P8_FIXED_LIT(raw, decimal)` is a function returning the raw value as a signed 32-bit number and ignoring `decimal`, which stays in the Lua call as the human-readable value, as in C.
- Representation: a fixed value is a Lua number holding the signed 32-bit raw value (range −2^31 … 2^31−1); every function returns a value normalized to that range. `p8_fixed_flr_int` returns a plain integer. The random state is a number in 0 … 2^32−1.
- Arithmetic is integer-exact: plain double arithmetic only where every intermediate stays below 2^53 in magnitude; otherwise the operands are split into 16-bit halves. The `bit` normalization is applied only to values in its exact range. Traps worth a comment where they occur: the 64-bit product of `mul` and `rnd` (up to 2^62/2^63) does not fit a double; `div` must truncate toward zero on the exact quotient, not on a rounded double quotient.
- `isqrt_u64` keeps the C binary search; its comparisons are exact in doubles because the argument is below 2^48.
- Out-parameter: `p8_fixed_rnd_from_state(state, x)` returns `result, new_state`; rnd(0) returns `0, state`. `p8_fixed_rnd` calls it on the module's state local. This convention is recorded in the step note for step 2.1 to adopt or override.
- No FFI, no `math.random`, no global variable: the module requires only `bit` and the quarter-wave module.

### The quarter-wave table

- `src/p8/quarter_wave.h` becomes the Lua module `p8.quarter_wave` in `game/p8/`, returning the 16385-entry table `p8_quarter_wave`, indexed from 0 as in C (the C index is used unchanged).
- The existing generator (`gen_quarter_wave`, behind `make sin-table`) gains an output mode for the Lua file; `make sin-table` writes both files. The Lua file is committed. The exhaustive sin/cos check is the proof the two tables are equal.

### The C reference binary

- A small C program beside `gen_quarter_wave` in `tools/`, linked with `src/p8/fixed.c` only, built into `tmp/`. It is outside the core sources (`CORE_SRCS`), so `float-guard`, `float-grep` and the other core guards do not read it; it uses no floating point anyway.
- It writes a stream of records: one section per C function (by C name), each record the inputs then the C result, 32-bit values in a fixed binary layout (little-endian), with a header and a trailing record count so the reader detects truncation. Sequence sections (global rnd from default seed, after `set_rnd_state`, rnd_default, rnd_state reads, rnd_from_state chains) record each call's inputs, result and resulting state.
- Two modes: the `make test` set (all edge values and combinations, every sin/cos angle, the rnd sequences, plus a pseudo-random sample sized to the budget), written to a file under `tmp/` by a make rule depending on the generator and the C library; and the full sweep (millions of values in all, count and seed as arguments), written to standard output.
- Inputs come from the C side only; the Lua test does not regenerate them. The pseudo-random inputs use a fixed-seed generator local to the binary, never the library's own `rnd`.

### The Lua test

- One file in `tests/lua/`, run by the system `luajit` (installed by `tools/love_install.sh`) with the JIT on, from the repository root; it extends `package.path` to the game directory and requires `p8.fixed`.
- Argument: the reference file path, or `-` for standard input. It decodes every record, calls the Lua function of the section's name, compares raw values, and reports up to 5 mismatches per function plus a per-function count; exit status non-zero on any mismatch, unknown section, malformed header or wrong record count. A green run prints one summary line (records checked).
- It drives sequence sections against the module's own global state, so the default seed is checked by the first draw of a fresh module.

### Make targets and timing

- A new target runs the Lua test on the `make test` reference file; it is listed directly among `test`'s prerequisites, placed by its measured duration (longest first). It is not a fake check (it does not run `tmp/fake_love`), so it is not added to `FAKE_LOVE_CHECKS`, but it follows rules 1, 2 and 4 of the design section: own target, one LuaJIT process, comparison inside that process, no shell pipeline, 100 ms budget.
- The `make test` sample size is set from measurement so the target fits 100 ms on the container. If the whole sweep of millions fits that budget and the gate, it stays in `make test` and there is no separate target. Otherwise (the expected outcome) a separate target pipes the binary's sweep mode into the Lua test; it is outside `test`, `e2e` and `test-all`, has a `## ` help line of at most 20 words, and joins `LOCKED_GOALS` (it builds into `tmp/`), with `CLAUDE.md`'s build section updated to name it among the locked targets.
- The step runs the design's protocol (worktrees under `tmp/`, warm-up, 11 rounds rotating order, paired medians, ≤ 3 % against both "before" and `8dff812`, 11 more rounds if needed). Over 3 % after 22 rounds → shrink the `make test` sample (the edge set always stays) and re-measure. The results go in the step 1.2 note in the format rule 4 lists.

### Checklist coverage (`make checklist STEP=1.2`, from step 1.1)

- Step 1.1's checklist (`tools/checklist.lua`, data in `tools/checklist.txt`, listing in `tmp/checklist.txt`) assigns `src/p8/fixed.c`, `src/p8/fixed.h` and `src/p8/quarter_wave.h` to step 1.2. The gate for "the checklist covers `fixed.h`" is `make checklist STEP=1.2`: before this step it fails on exactly 27 items (26 functions: the 11 inline functions of `fixed.h`, the 13 functions it declares and `fixed.c` defines, and the file-local `isqrt_u64` and `quarter_wave_at`; plus the table `p8_quarter_wave`); at the end of the step it passes. `make checklist` is outside `make test`, so it does not enter the timing gate.
- The checklist finds a Lua item by the same-file, same-name rule: C `src/p8/X.[ch]` → `game/p8/X.lua`, and a function counts when the Lua file defines it at line start as a global, a `local function`, or a module field (`function M.name(` or `M.name = function`). So every exported function is written `function M.p8_fixed_…(` (or as a local function then assigned), not only listed in a returned table constructor, which the scanner does not see; the two file-local helpers are `local function`s; `p8_quarter_wave` is assigned at line start (`local p8_quarter_wave = {`) in `game/p8/quarter_wave.lua`.
- With the C names kept, no data edit is needed; a Lua name that has to differ gets a `lua` exception line in `tools/checklist.txt`. Macros and constants are not checklist entries; `P8_FIXED_INT`, `P8_FIXED_LIT` and the constants are still ported, as faithful copies.

## Implementation Chunks

1. **Reference commit.** `design.md` rule 4 names `8dff812`; the step 1.2 note is created with the choice and its reason. Measure `8dff812` and HEAD once with the protocol to record the reference's figures (docs only; no code).
2. **Harness and integer arithmetic.** The C reference binary (record format, `make test` mode with edge values and pseudo-random sample), the Lua test reader and reporter, the make target in `test`, and in the Lua module: constants, macros, `from_int`, `add`, `sub`, `mul`, `div`, `neg`, `flr`, `flr_int`, `abs`, `sgn`, `mid`, `band`, `bor`, `mod`, `shl`.
3. **Roots and trigonometry.** `isqrt_u64`, `sqrt`, `pow075`, the Lua quarter-wave table and its generator mode in `make sin-table`, `quarter_wave_at`, `cos`, `sin`, with the exhaustive angle sections.
4. **Random generator.** LCG constants and seed, `rnd_from_state`, `rnd`, `rnd_state`, `set_rnd_state`, `rnd_default`, with the sequence sections; the out-parameter convention in the step note.
5. **Budget, sweep and record.** Sweep mode of the binary; measure the Lua target; size the `make test` sample; split into the separate sweep target if over budget (help line, `LOCKED_GOALS`, `CLAUDE.md`); run the timing protocol against "before" and `8dff812`; record in the step note; `make checklist STEP=1.2` passes.

## Testing Decisions

- A good test here checks external behaviour only: the value each public Lua function returns (and the state the random functions leave) for given inputs, against the C library's value for the same inputs. No test inspects how the Lua computes.
- Tested: `p8.fixed` (every function and macro, through the C oracle) and, through sin/cos over every angle, `p8.quarter_wave`. The C reference binary is not unit-tested on its own: the Lua test's header and count checks catch a malformed or truncated stream, and a function the binary omits shows up as a section the test expects and does not find (the test holds the list of every C name it must see).
- Red first: for each chunk, the binary's section is added and the Lua test is seen failing (missing function, then wrong value) before the Lua function is written.
- Prior art: `tests/test_fixed.c` (the C library's own unit tests, whose edge cases — overflow wraps, from_int wrap, 128*128 overflow — are the seed of the edge set); `tools/gen_quarter_wave.c` and `make sin-table` (generator binary and generated table pattern); the `unit-run-*` targets and `FAKE_LOVE_CHECKS` in the Makefile (one target per check, under `-j`).
- Coverage gate: `make checklist STEP=1.2` (step 1.2 counts `0/26 functions, 0/1 tables` before, `26/26, 1/1` after); run at the end of each chunk to watch the count rise.
- No C unit test is added or changed; `tests/test_fixed.c` stays as it is. The e2e are not run for this step (plan 2 rule); `make e2e` is unaffected since no C game code changes.
